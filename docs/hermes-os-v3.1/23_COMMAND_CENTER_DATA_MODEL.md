## 1. Purpose

This document defines the complete data model for the Hermes Command Center: every entity, its fields, types, relationships, and constraints. These entities form the Command Center's source of truth — every piece of information displayed in the UI traces to one of these records.

This model is designed to be **immutable-first**: records are written once and never updated in place. State changes are recorded as new events, not as mutations to existing records.

---

## 2. Design Principles

### 2.1 Immutable Task-State History

Every task state transition produces a new `task_state_event` record. The current state of a task is the most recent event. The full history is preserved for audit, debugging, and agent scorecard computation.

```
Task TASK-0042 state history:
  DRAFT          → task_state_event #001 (2026-07-31T09:00:00Z)
  PLANNING       → task_state_event #002 (2026-07-31T09:15:00Z)
  BUILDING       → task_state_event #003 (2026-07-31T09:30:00Z)
  SUBMITTED      → task_state_event #004 (2026-07-31T10:45:00Z)
  ...
```

No field that represents task state is ever updated. The task record itself holds only identity and immutable fields (ID, creation timestamp, title at creation time).

### 2.2 Evidence Links

Every entity that makes a claim (review finding, test result, deployment record) must include a link to the actual evidence artifact — a file path, a commit hash, a screenshot reference. Claims without evidence links are not rendered in the Command Center.

### 2.3 Auditability

Every record carries:
- `created_at` (UTC timestamp)
- `created_by` (agent or user identity)
- `source_event` (the event that triggered this record's creation)

This enables full traceability: "Who created this record, when, and why?"

### 2.4 Recoverability

The filesystem-first design means the entire system state can be reconstructed from the `.hermes/` directory tree. If the SQLite database is lost, it can be regenerated by scanning the YAML/JSON files. The filesystem is the durable store; any query-optimized store is a cache.

### 2.5 Constraints

Foreign keys are conceptual rather than enforced at the database level — the filesystem-first design means relationships are validated at read time, not write time. However, the Command Center UI must validate referential integrity on display and surface broken references as errors.

### 3.2 Future: SQLite for Query-Heavy Views

When the number of records exceeds ~1,000 in any entity type, a SQLite database (`state.db`) can be generated as a query-optimized cache. The filesystem remains the authoritative store. The SQLite database is rebuilt from filesystem files on startup and updated incrementally on write.

The SQLite schema mirrors the entity definitions below. This document defines the logical model; the physical schema is derived from it.

## 4. Entity Definitions

### 4.1 Project

**Purpose:** Top-level organizational unit. Groups releases and tasks.

**File:** `.hermes/data/projects/{project_id}.yaml`

| Field | Type | Required | Description |
|---|---|---|---|
| `project_id` | string (slug) | ✓ | Unique identifier, e.g. `avoa`, `hermes-os` |
| `name` | string | ✓ | Display name |
| `description` | string | | |
| `status` | enum | ✓ | `active`, `paused`, `completed`, `archived` |
| `repository_url` | string | | GitHub repository URL |
| `created_at` | datetime | ✓ | ISO 8601 |
| `created_by` | string | ✓ | Agent or user identity |
| `updated_at` | datetime | ✓ | Last modification timestamp |
| `archived_at` | datetime | | When status changed to `archived` |

**Relationships:**
- One-to-many: Project → Releases
- One-to-many: Project → Tasks (via task.project_id)

**Constraints:**
- `project_id` must be unique across all projects
- Status transitions: `active` → `paused` → `active`, `active` → `completed`, `active` → `archived`
- Archived projects cannot be reactivated (must create new project)

- Subtask task_ids follow pattern `{parent_task_id}-S{n}`

### 4.4 Task Contract

**Purpose:** The immutable contract that defines a task's scope, constraints, and requirements. Separate from the task record to allow contract versioning.

**File:** `.hermes/data/tasks/{task_id}/contract.yaml` (co-located with task)

The task contract is the task record itself (see §4.3). In practice, the task record IS the contract. For contract versioning, if a task is re-scoped, a new task is created with a reference to the original.

---

### 4.5 Task State Event

**Purpose:** Immutable log of every state transition a task undergoes. Forms the audit trail and enables state reconstruction.

**File:** `.hermes/data/tasks/{task_id}/state_events.yaml` (append-only)

| Field | Type | Required | Description |
|---|---|---|---|
| `event_id` | string | ✓ | Unique event identifier |
| `task_id` | string | ✓ | FK → Task |
| `from_state` | enum | ✓ | Previous state (null for creation) |
| `to_state` | enum | ✓ | New state |
| `transition` | enum | ✓ | The transition name, e.g. `DRAFT→PLANNING` |
| `triggered_by` | string | ✓ | Agent or user identity |
| `reason` | string | | Human-readable reason for transition |
| `evidence_refs` | list[string] | | Links to evidence artifacts supporting the transition |
| `timestamp` | datetime | ✓ | |
| `metadata` | object | | Arbitrary key-value for transition-specific data |

**Valid states:** `DRAFT`, `PLANNING`, `BUILDING`, `IMPLEMENTATION_SUBMITTED`, `AUTOMATED_VALIDATION`, `VISUAL_QA`, `FINDINGS_TRIAGE`, `FINAL_VALIDATION`, `READY_FOR_AMJAD`, `APPROVED`, `MERGED`, `DEPLOYED`, `MONITORED`, `CLOSED`, `BLOCKED`, `REJECTED`, `CANCELLED`, `FAILED`

**Relationships:**
- Many-to-one: TaskStateEvent → Task

**Constraints:**
- `from_state` → `to_state` must be a valid transition as defined in Doc 06 (Task Lifecycle)
- Events are append-only; never modified or deleted
- Ordering is by `timestamp` — if two events have the same timestamp, secondary sort by `event_id`

- Scorecards are regenerated at the end of each period from raw task/event data
- Minimum 5 tasks per category before scorecard is considered valid for routing

## 6. Event Log

All state-changing operations produce events appended to `.hermes/event_log/events.jsonl`. Each event is a JSON object with:

```json
{
  "event_id": "evt-{uuid}",
  "event_type": "task.state_changed | agent.run_started | review.finding_created | ...",
  "entity_type": "task | agent_run | review | deployment | ...",
  "entity_id": "...",
  "data": { ... entity-specific payload ... },
  "timestamp": "2026-07-31T14:32:00Z",
  "source": "hermes-core | command-center | ci-pipeline"
}
```

The event log enables:
1. Reconstructing any entity's state at any point in time
2. Triggering Command Center UI updates (WebSocket push)
3. Computing agent scorecards from raw events
4. Debugging and post-mortem analysis

## 9. Implementation Notes

### 9.1 HOS-3 Scope

In HOS-3, only the filesystem storage layer and the event log are implemented. Entities are written as YAML files. No SQLite database, no UI. The goal is to establish the data foundation.

### 9.2 HOS-4 Scope

In HOS-4, the Command Center MVP reads from the filesystem and renders the first modules. If query performance is insufficient, a SQLite cache is introduced. The filesystem remains authoritative.

### 9.3 Validation

On every read, the Command Center must:
1. Validate YAML schema against entity definitions
2. Verify file hashes for integrity
3. Cross-reference entity references (broken references → warning in UI)
4. Surface any validation failures prominently

### 9.4 Migration from v3.0

Existing v3.0 data (task contracts in `.hermes/contracts/`, decisions in `.hermes/registers/`) must be migrated to the new structure. The v3.0 data is limited and can be manually converted. A migration script is part of HOS-3.
